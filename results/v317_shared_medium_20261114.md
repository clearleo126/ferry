# v31.7 host 作共享介质 vs 复制副本（carry）× GPU 容量 三档（2026-11-14）

数据：`/data1/ferry_artifacts/v316_shared_medium/`，30 份 log（hot∈{128,256,512} ×
kv-mode∈{delta(carry),drop} × n=5，rep 外层交错）。代码 = `d74675a`，无改动。

## 0. 问题

主线一直是"完整 KV 驻 pinned host、GPU 只持有界热集"（§1 的标题句），且 `h_slab_`
的回填读取与卡号无关（`wla_multigpu.cuh:2517`）—— **物理上 host 已经是 4 卡共享介质**。
但从没把它当成决策变量：迁移仍把热集从 victim 的 `d_cache_` gather→staging→scatter
复制过去（`wla_multigpu.cuh:1393-1415`），而这份数据 host 侧本来就有源。

"不复制、只改归属、消费卡此后按需从 host 读" = `--kv-mode drop`。
§19.2① 的既有结论是 **carry 恒优于 drop（581 配对，0 次翻盘）**，
但那是在 **hot=128 / hit=0.842 单点**上得到的。本实验扫容量，检验它是不是单点结论。

解析判据（复制 vs 共享）：

```
复制（carry）成本 ≈ live_b              # 只搬驻留槽（delta）
共享（drop） 成本 ≈ remain × miss_b      # 此后每步 miss 都回 host 读
⇒ 共享更省 ⟺ remain × miss_b < live_b
```

## 1. 口径

公共 flag 与【31】一致，但**关掉 vchan**（`--vchan-bw 0`，无虚拟网络、无慢卡、
`skew=balanced`），以隔离"复制 vs 共享"这一条轴；`--modes 2,3`（C/E），
`--mig-bw 25 --mig-scope hot --remote-tax 1 --tax-account full`，
`--cap-mode perreq --prefix-group 4`，trace `qwen7b_g4_s96_quest.bin`。

复现：`bash /data1/ferry_artifacts/v316_shared_medium/run_matrix.sh`，
`python3 /data1/ferry_artifacts/v316_shared_medium/parse.py`。
（`unset LD_LIBRARY_PATH` 必须，见【31.1】。）

## 3. 判定

### ① 字节账：共享（drop）在**所有**容量点都更省，且随 hit 单调放大

−184.5 / −459.8 / −650.6 MB（−3.6% / −13.0% / −18.6%），4–5/5。

解析判据在 hot=128 上被定量验证：`remain≈69`、`miss_b = 64×28×16KB×(1−0.842) = 4.64MB`
⇒ 共享的替代成本 320MB；实测 live_b = **516.5MB** ⇒ 预测 carry 多付 **+196MB**，
实测 **+184.5MB**（偏 6%）。hot=512：预测 live_b 1020 − 117 = +903MB，实测 +651MB
（偏 28%，因为高 hit 下 remain×miss_b 项进一步缩小，且迁移请求数变少）。

⇒ **§19.2① "carry 恒优于 drop" 的字节方向在 hot=128 上也不成立**（本次 +184.5MB 反向）。
两者口径不同（§19.2 是快照反事实、单步 × 视野累积、581 配对；本次是整跑 30 次、
含完整后续回填），**不能直接判 §19.2 错**，但"恒优"这个词必须撤掉。

### ② 时间账：共享只在**容量接近工作集**时才不亏，且翻转点由 hit 决定

+435.5 → +197.0 → −60.6 ms（胜 1/5 → 2/5 → 4/5）。**跨三档单调**，这是本节的主结论：
**"host 当共享介质"不是普适更优，它需要一个前提——GPU 侧容量已经大到冷启动不痛。**

⚠️ hot=512 的 −60.6ms **不要当强证据**：配对范围 [−413.9, +390.0]，
且中位数之差不等于中位之差（delta 的 r2 是 3475.9ms 离群，边际中位会给出 +390ms 的假象；
配对才是有效量）。方向可信，幅度在 3090 的 ±10–25% 噪声内。

### ③ 时间损失不来自字节，来自**负载均衡质量**

| hot | delta imb 中位 | drop imb 中位 | Δms |
|---|---|---|---|
| 128 | 0.156 | **0.283** | +435.5 |
| 256 | 0.177 | **0.306** | +197.0 |
| 512 | 0.156 | 0.195 | −60.6 |

drop 的 `imb`（完成数变异系数）在低容量档接近 2×。机制假设（未分离）：
冷启动让消费卡在窃取后的一段时间内变慢 → 均衡环路继续判它"落后" → 继续窃取/继续冷启动，
形成**冷启动-再窃取的自我激励**。这也解释了为什么"字节更省却更慢"——
与 §19.3 的"字节最优 ≠ 系统最优"同源，但这次的机制是**调度质量退化**而非单步成本误估。

## 4. 对主线的意义

1. **不能把"host 作共享介质"写成贡献**。它是一条**容量条件成立**的替代实现：
   hot≥512（≈ 每请求 128 slot/层、hit 0.94）时省 18.6% 字节、时间不亏；
   hot=128 时省 3.6% 字节但慢 17%。与 §29/§30 同纪律：机制成立、条件受限、不入主线。
2. **但它是"迁移必要性"的一个真实边界证据**：当 GPU 容量接近工作集时，
   **复制热集这件事本身就变成冗余的**（数据在共享 host 上已有一份）。
   这句话可以写进讨论，用来界定"什么情况下不该迁移数据、只该改归属"。
3. **解析判据 `remain×miss_b vs live_b` 被验证**（6% 误差），可作为
   `--mig-scope auto` 的姊妹判据：现在的 auto 只在"搬不搬 home"上用它，
   而"搬 hot 还是共享"应该用同一条式子。**这是下一步唯一值得做的改动**：
   把 `do_home` 的三态（不搬 / 搬热集 / 只改归属）合成一个判据，
   并让它在 hot≥256 时倾向"只改归属"。
4. E−C 在本次口径下无稳定符号（hot=128 逐 rep +532/−216/+664/−43/+713），
   与【31】"闸门无独立贡献"一致，不再单独解释。

## 5. 局限

- **载荷是合成的 tile 模式**，`wla_slot_off` 按 `block % hot_blocks` 寻址；
  hot=512 时 1044 块映射到 512 个槽（2× 混叠），hot=128 时 8× 混叠。
  这是模型既有属性（hot=128 的历史结论同样在这个前提下），**只影响字节语义，
  不影响计时与搬运量**——但写论文时必须declare："同组同 block_id 视为同内容"。
- hot=512 + `cap_mode=perreq` + `prefix_group=4` ⇒ 组容量 2048 > 实际 1044 块，
  **等于无容量压力**，是退化端点；hot=256 才是"有压力但仍高 hit"的现实档。
- 无慢卡、无 vchan、单 seed、`skew=balanced`；B=25GB/s。
- 只测了 `n=5` 的 makespan，`imb` 只作机制指示不做主张。
- drop 在本模型里**不付 host 侧 LRU/逐出成本**（slab 永不失效）⇒ 共享略被高估；
  反向也成立：真实系统里被迁请求的 host 副本可能已被逐出，drop 会更差。
  两个偏差方向相反，未定号。
