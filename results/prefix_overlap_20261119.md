# PAT 式前缀打包在 Ferry miss trace 上的可达上界（离线统计）

**问题**：PAT（ASPLOS'26，TJU+Stevens）主张 prefix KV cache 只省存储与算力、不省
global memory 的访问量，靠把共享前缀的 query 打进同一 CTA 让一份 KV tile 只加载
一次（attention −53.5%、TPOT −17~93.1%）。Ferry 的同构边界是 host link（同卡 k 个
请求各拉一遍共享前缀 = k 次 PCIe 传输）。**问：在 top-k 稀疏选择流上，这个摊销还剩多少？**

**结论**：PAT 的**同步打包机制**在稀疏域只剩 **4.3–5.8%**；但前缀的**驻留期复用**
是真的（等内存下 refill 字节 −21.8~39.0%，异组对照 ≈0）。后者不是新优化——真实引擎的
prefix cache 已经免费提供，而 Ferry 的逐请求驻留模型没有建模它 ⇒ 这是一条**口径修正**，
不是一条新主线。

工具：`tools/prefix_overlap.py`（纯离线，不跑 GPU；block = 4 token，字节按
`MissSpec::c4_bytes` = 8 KB）。数据：`/data1/ferry_artifacts/traces/` 三档 Qwen2.5-7B
真实 miss trace（g4 = 每组 4 请求共享前缀，12 组，sel_pages=16，method=quest）。

## 口径

- **M1**：同一 (step, layer)、同卡 k=4 个同组请求的 selected 多重集，`Σ|multiset| / |distinct|`。
  上界口径 = 理想共置 + 同步 decode（vLLM 连续批处理本来就是同步 step）。
- **M4**：同样算法但 4 张卡各取一个**异组**请求 —— 当前放置下的对照。
- **M2**：等设备内存（k×H vs k×H），组内聚合频次 top-kH 的静态热区 vs 逐请求 top-H 的覆盖率。
- **M3**：等设备内存，卡级共享 LRU(kH) vs k 个逐请求私有 LRU(H)；访问流按**逐 step 交错**
  构造（串行拼接会给共享臂凭空送时间局部性）。异组对照 = 同样 kH 缓存但 4 个请求互不共享前缀。

## 三条机制读法

1. **PAT 的 pack 在稀疏域几乎不成立（~5%）**。dense attention 下打包天然合法，因为共享前缀
   反正要全读；top-k 稀疏下选择由**当前 query** 决定，同前缀不同后缀的两个请求只共享
   "哪 16 个 page" 的部分排序。前缀占上下文 44–50%，但每步只选 16/256+ pages，
   叠加结果是同 step 只重合 5%。**这正是 PAT 不需要、而 Ferry 必须验的折扣，现在有数了。**
2. **收益的真实来源是"驻留期重叠"，不是"同一时刻去重"**。5% 的同 step 重合却换来 22–39%
   的 refill 减少：共享前缀块被每个请求的私有小缓存反复逐出（hot=128 只有 2 步工作集），
   合一后只要在窗口内任一请求碰到就算命中。这与 实验设计【32】"host 作共享介质"是同一物理事实的缓存侧版本。
3. **异组对照 ≈0 是关键**。同样内存、同样 LRU、同样交错顺序，只是请求互不共享前缀 ⇒
   收益消失。所以这 22–39% 全部归因于**前缀身份**，不是容量池化的一般红利。
   注意 32k / hot=512 的对照为 −16.2%（池化本身有害），说明大 context 下共享容量被
   不同工作集互相污染，前缀只是把它抵消回来。

## 对主线的影响（诚实版）

**(a) 时间上不足以成为主张。** 项目自己的口径：HiSparse 有界驻留下迁移传输仅占 makespan
极小比例，真正瓶颈是回填；refill 字节减少 22–39% 若按 refill 占比 ~2% 折算，makespan
改善在 0.5% 量级 —— 落在噪声里。**不能写成"前缀感知带来 X% 加速"。**

**(b) 但暴露了一条口径有效性威胁（这条更重要）。** 真实引擎（vLLM APC / RadixAttention）
的 block table 按引用共享前缀块，一张卡上**只有一份物理驻留**；而 Ferry 的
[kv_exec.cuh](../src/workloads/kv_exec.cuh#L55-L59) `cache_slot_off(sp, req, layer, block)`
按 `req` 索引，同卡 k 个请求各有一份私有槽位 ⇒ **refill 字节被系统性高估 ~22–28%**
（相对），且随组内请求数 k 放大。跨臂比值大概率不受影响（同偏），但：
  - 论文里报 **refill 绝对字节** 必须注明口径；
  - **κ→refill 的斜率**（【19】②，斜率 456MB/decade）建立在同一偏置上，方向不受影响、
    绝对幅度需重述；
  - v31.7【32】的"host 共享 vs carry 副本"对照里，副本臂若也按逐请求驻留计价，两臂的
    前缀分量都偏高，结论方向不受影响，但差距会被压缩 —— 需复核。

**(c) 对 PAT 的定位**：不是竞争对手，是一段可写的边界。可以主张"prefix 的访问摊销在
稀疏 top-k decode 下从同步去重退化为驻留期复用，且后者已被 prefix cache 免费提供"——
这是对一篇 ASPLOS 论文的边界补充，比再提一个阈值规则值钱。

## 建议的下一步（都不大）

1. **实现块级共享驻留区**（block_id 键控，`cache_slot_off` 去掉 `req` 维），默认关。
   验收：refill 字节 −20~30%、makespan 变化落噪声内。**目的是口径正确，不是性能。**
2. 若要把它变成性能主张，先测**refill 占 makespan 比例 >2% 的档**（hot=128 + 32K
   context 的 HiSparse 配置），再决定值不值得做成"前缀感知驻留分配"。

## 局限

仅 quest 选择法（无 mass 对照 trace）；组内 4 请求、等长输出、12 组；单模型；
前缀共享为**构造**的 2K/16K 完全一致前缀，真实 agent 负载的层级化前缀（system prompt
+ 工具 + RAG）重合度更高但也更碎片化，需要 ShareGPT 实采样验证；M3 只跑了 5 个组。
